## Phase 4.1 — Enable and Validate AI Integration End-to-End — ✅ DONE (2026-09-09)

**Trigger:** User request — focus v4 on AI integration instead of Charts; "turn on and prove out what's already built" (chosen over building a new AI feature or expanding provider support, at a decision point where the AI subsystem turned out to be fully built but switched off with no evidence it had ever run against a real provider).

**Items:**
- ✅ 4.1.1 `AI_ENABLED=true` in `.env`. Local Ollama confirmed already running (several models available). A second real provider — an OpenAI-compatible gateway serving a Claude Opus model, with a live API key — was also configured for this test.
- ✅ 4.1.2 Fixed unregistered provider name: `AI_PROVIDER` was set to a descriptive label not in the registered set (`ollama | lm_studio | openai | openrouter | anthropic | openai_compatible`); `build_provider()` correctly rejected it, silently marking the provider always-unhealthy. Fixed to `AI_PROVIDER=openai_compatible` (the existing generic type for custom OpenAI-dialect endpoints) with `AI_BASE_URL` corrected to include the required `/v1` path. `.env.example`'s AI section comment was also stale (missing `lm_studio`/`openai_compatible`/`openrouter`) — corrected with guidance on `openai_compatible` + the `/v1` requirement.
- ✅ 4.1.3 **Real bug found and fixed:** `AIManager._get_provider()` (`backend/ai/manager.py`) applied the primary's `base_url`/`model`/`api_key` to *every* provider in the fallback chain — so a fallback (a different service by definition) silently inherited the primary's config instead of using its own. With primary=the paid gateway and fallback=`ollama`, the "ollama" fallback was being pointed at the *primary's* base_url asking for the *primary's* model — carrying the exact same failure as the primary instead of actually falling back. Fixed: only the primary (`name == settings.provider`) gets the configured base_url/model/api_key; every other chain entry gets `None`, letting `build_provider()`'s own per-provider defaults apply. Verified live: `GET /api/ai/status` for `ollama` went from `healthy=false` (silently misconfigured) to `healthy=true` after the fix, with zero new `.env` entries needed.
- ✅ 4.1.4 Ran a real end-to-end analysis: `POST /api/ai/analyze?symbol=SPY&timeframe=1d` against the live backend/database and the real gateway provider — returned a schema-valid `AnalysisResponse` (trend, confidence, supporting/risk factors, a flagged timeframe conflict) in ~4s. Confirms the full pipeline (`build_context` → `ai_manager.complete` → real HTTP call → `parse_ai_reply` → Pydantic validation) works live, not just under mocks.
- ✅ 4.1.5 **Real bug found live via the frontend:** `AIAnalysisPanel`'s "Re-run" 405'd every time. `api.analyzeSymbol()` (`frontend/src/services/api.ts`) called the shared fetch helper with no `method`, defaulting to GET; `POST /api/ai/analyze` is POST-only. Existed since the endpoint was built — never surfaced with AI off. Fixed by adding `{ method: 'POST' }`; verified live (GET→405, POST→200) and swept the rest of `api.ts` for the same bug class (no other instances found).
- ✅ 4.1.6 Enabling AI for real broke 3 pre-existing tests in the unrelated NL-search feature (`backend/nl_search/`, `backend/api/nl_search/router.py`), each importing its own `ai_manager` reference independently — mocking one didn't mock the other. `test_parser.py::test_garbage_falls_to_default` didn't mock AI at all and got a confident-but-wrong AI parse of nonsense input instead of the expected rules→AI→default fallthrough; `test_nl_search_router.py::test_rule_based_query_returns_200` / `test_explain_true_includes_explanation` mocked the parser's `ai_manager` (query translation) but not the router's separate one (result explanation, `explain=True` by default) — so a real explanation got generated where both tests expected none. All three fixed by mocking the actual reference each code path uses.
- ✅ 4.1.7 **Real bug found live via the frontend, second time:** clicking "Re-run" again surfaced `AI response could not be parsed: ... trend Input should be 'bullish', 'bearish', 'neutral', 'mixed' or 'uncertain' ... input_value='downtrend' ... Provider: ollama. Model: llama3.2.` The primary was briefly unavailable (see the flakiness note below), the request fell to Ollama, and llama3.2 echoed the ENGINE's own trend vocabulary (`TrendDirection`/`TrendClassification`: `uptrend`/`downtrend`/`sideways`/`strong_bullish`/`no_signal`/etc. — all visible in the context it's shown) instead of translating to the 5-word output vocabulary the prompt actually specifies. A predictable near-miss, not gibberish. Added a `field_validator("trend", mode="before")` on `AnalysisResponse` (`backend/ai/prompt.py`) normalizing known engine-vocabulary synonyms before the strict `Literal` check runs; anything not in the map still fails validation unchanged (confirmed: the pre-existing `test_rejects_trend_outside_vocabulary` still passes). Also sharpened `SYSTEM_PROMPT` rule 2 with an explicit translate-don't-copy example — a prompt tweak alone isn't reliable enough on its own with smaller local models, so the code-level normalization is the load-bearing fix.

- ✅ 4.1.8 **Real bug found live, third time:** after the user changed `.env` to try a different model and dropped the `/v1` path `openai_compatible` requires (flagged to the user, not silently fixed — their config to decide on), `POST /api/ai/analyze` returned a bare `{"detail": "Internal server error"}` instead of the graceful `UncertaintyResponse` the module promises for every bad-AI-response case. Root cause: `OpenAICompatibleProvider.complete()` (`backend/ai/providers.py`) got HTTP 200 with an HTML body (the gateway's own web UI, reached because the missing `/v1` resolved to the wrong route) — `r.json()` raised a raw `json.JSONDecodeError` that nothing caught, unlike every other bad-response shape (4xx/5xx/malformed payload), which are deliberately converted to `ProviderUnavailable`. Fixed by wrapping `r.json()` the same way; found and fixed the identical gap in `AnthropicProvider.complete()` in the same file. Verified: the same request now correctly returns `UncertaintyResponse` instead of a 500 (the `/v1` config mistake itself is unfixed — that's the user's call).

**Known, not fixed (at the time):** the primary gateway's health-check endpoint (`GET /v1/models`) is flakier than its actual completion endpoint (`POST /v1/chat/completions`) — `/api/ai/status` sometimes shows the primary as unhealthy even when a real analysis call through it succeeds moments later. Not chased further then: the 4.1.3 fix means a false-negative health check just costs one extra hop to a correctly-configured Ollama fallback, not a broken request — which is exactly the path that surfaced 4.1.7. **Resolved in 4.2.9** (see Phase 4.2 below): a single retry before reporting unhealthy.

**Tests:** 6 new (`backend/tests/ai/test_ai_manager.py::TestFallbackProviderIsolation` — asserts a fallback's `base_url`/`model` are its own defaults and it never receives the primary's `api_key`); 2 pre-existing tests fixed for now-real environment coupling (`AI_ENABLED=true` is genuine `.env` state as of this phase, not a test fixture default — fixed via `_env_file=None` to test `AISettings`' actual field defaults in isolation, matching the existing house pattern from `test_aux_data_settings.py`); 3 more pre-existing tests fixed per 4.1.6; 1 new subtest-parametrized test per 4.1.7 (`test_phase16_analyze.py::test_normalizes_engine_vocabulary_synonyms`, 11 cases); 2 new tests per 4.1.8 (one per provider class, non-JSON-200 body).

### Addendum (2026-09-09) — Items 4.1.9-4.1.16: hardening pass from continued live use

4.1.1-4.1.8 proved the pipeline works end-to-end. Actually *using* the
now-live features (AI Stock Search searches, AI Analysis re-runs) kept
surfacing more real, independent bugs — the same "turn the key and see
what's actually wired wrong" mode 4.1 opened with, just continued past
the first end-to-end success instead of stopping there. Real user
reports each time, not a self-directed sweep.

- ✅ 4.1.9 **AI Stock Search "Market" scope dropdown was silently ignored, then found to be unfixable as designed.** `commit c22443d` fixed the immediate bug: the Watchlist/Market dropdown's value only ever reached `NLFilters.scope` via the rule-based parse path, and even there only through `setdefault` — the AI parse path and the graceful-default path both silently reverted to the schema's own `"watchlist"` default regardless of the dropdown. Fixed in `backend/nl_search/parser.py`'s `parse_query()` by applying `base["scope"]` unconditionally after parsing, not threaded through each path. User re-tested live and still saw watchlist-only results with "Market" selected — deeper investigation (`commit af40295`) found the real issue: there is no market-wide scanning capability anywhere in the app. `execute_query()`'s "market" branch just reads whatever's incidentally cached from watchlist scans; it was never wired to a real universe. Presented three real options (build market-wide scanning, relabel the dropdown, or remove it); user chose removal. `NLSearchBar.tsx`'s scope `<select>` deleted; search always uses watchlist scope now, the one path that's real. The backend scope-override mechanism from the first fix stays in place (harmless, unreachable from the UI, correctly tested).
- ✅ 4.1.10 **AI Stock Search latency + a real concurrency bug: AI calls were blocking the whole server, not just the request.** User asked to optimize the feature (`commit 5d0c593`). Investigation found `POST /api/nl-search` is `async def` but both its AI calls (query translation, result explanation) went through synchronous `httpx.Client`, called directly instead of via `asyncio.to_thread` — every AI-backed search froze the entire FastAPI event loop (WebSocket price broadcasts, every other request) for the full external round-trip. Proved live: a concurrent `/api/system/status` call (normally ~3ms) took ~2s while an AI call was in flight; after wrapping both calls in `asyncio.to_thread` (the same pattern already used in `backend/api/ai/router.py`), the concurrent call stayed at 5-10ms during a 6.7s AI call. Also: bare "bullish stocks"/"bearish stocks" (no timeframe/ranking keyword) matched no rule and paid a full AI round-trip for something trivial — added a last-resort direction-only rule (verified live: `parser_used` went `ai` → `rules`). Added a bounded LRU cache for successful AI translations (query text is a pure input to that call — same English always maps to the same filter shape) so repeat queries skip the round-trip entirely.
- ✅ 4.1.11 **Real bug found via a user report, not a self-check: "AI Stock Search sometimes says no symbols matched" traced to a trend-engine calibration bug affecting every confidence-gated feature in the app, not just search.** (`commit 041ec0b`) Confidence was literally `abs(avg_signal)` — the same weighted signal value used to decide direction at a threshold of just 0.15-0.35. So the instant a trend was confirmed, confidence sat at 0.15-0.35 by construction, permanently below every `min_confidence >= 0.5` default used app-wide (NL search, `DailyBullish`/`DailyBearish`, `MinTimeframeBullish`/`Bearish`, `MTFAlignment`, the scanner's own `MULTI_TIMEFRAME_BULLISH`/`BEARISH` signal). Verified live: watchlist symbol DVLT had a genuine 1d downtrend (confidence 0.365) that "bearish stocks" still couldn't find. Fixed in `backend/trend/trend_engine.py` by rescaling confidence so crossing the direction threshold maps to 0.5 (not the threshold's own raw value), continuous through the sideways boundary, maxing at 1.0. Confirmed isolated to the `confidence` field only — `score`/`classification` come from a separate `raw_score` variable, untouched. Verified live post-fix: real downtrending watchlist symbols read confidence 0.63-0.69 (was 0.2-0.6), and "bearish stocks" now correctly surfaces them.
- ✅ 4.1.12 **AI Stock Search trend/signal columns were the one place in the app not using the existing green/red/yellow convention.** (`commits ef452ff`, `f407baf`) Every other trend-direction display in the app (`TrendCard`, `MTFScoreGrid`, `ConfluenceCard`, `ScannerPage`'s `.cell-trend` badges) already color-codes uptrend/downtrend/sideways; `NLSearchBar.tsx`'s `trendLabel()` rendered plain uncolored glyphs. Matched the existing exact hex values (`#22c55e`/`#ef4444`/`#eab308`) rather than inventing new ones. Signal chips (RSI oversold, MACD bullish/bearish, MTF bullish/bearish, High Vol) got the same treatment using the bullish/bearish classification `TopMoversCard.tsx` already uses for these exact signal names; `HIGH_VOLUME` (direction-agnostic) gets the neutral/yellow treatment.
- ✅ 4.1.13 **Real bug found live via the frontend, fourth time: AI Analysis's "Re-run" showed "Failed to fetch."** (`commit 0cd8653`) Root cause: the configured `openrouter/free` model rate-limited (429). `OpenAICompatibleProvider.complete()`/`AnthropicProvider.complete()` routed any 4xx that wasn't 401/403/404/5xx into a deliberate `r.raise_for_status()` — "the request is broken, the caller should see it" — but nothing upstream ever caught the resulting `httpx.HTTPStatusError`; it propagated to FastAPI as an unhandled exception, which the browser surfaced as a network-level failure rather than a normal error response. 429 was miscategorized: it means the provider is temporarily unavailable, not that the request is malformed — moved it into the same recoverable bucket as 401/403/404/5xx in both provider classes. Deliberately left plain 400 alone (an existing test, `test_complete_raises_for_status_on_400`, documents that a genuinely malformed request should still fail loud — a prior intentional choice, not this bug). Verified live: the same analyze call that 500'd now returns 200 with the existing graceful "AI providers unavailable" uncertain response, CORS headers intact.
- ✅ 4.1.14 **`.env` audit found `AI_MAX_TOKENS=100000` — 100x the code's own default (1000), silently in effect for every AI Analysis call.** Neither frontend call site (`AIAnalysisPanel.tsx`'s Re-run, `AITemplatesPanel.tsx`) passes an explicit `max_tokens`, so both fell through to this setting. A plausible contributor to the 429s in 4.1.13 — many providers rate-limit by token budget, not just request count. Corrected to `2000` in the live `.env` (gitignored, no commit; `.env.example` already documented the correct `1000` default and needed no change — only the live file had drifted). `AI_TIMEOUT`/`AI_HEALTH_CHECK_TIMEOUT`/`AI_TEMPERATURE` audited in the same pass and confirmed already correct (matching code defaults / well-suited to the task).
- ✅ 4.1.15 **Stopped hardcoding temperature in the two NL search AI calls.** (`commit 920a5bb`) Query translation hardcoded `temperature=0.0` and result explanation hardcoded `0.3`, both ignoring `AI_TEMPERATURE`. Per explicit instruction, removed both overrides — translation is no longer special-cased as a "must be deterministic, fixed-vocabulary" task; both calls now use the configured setting like every other AI call in the app. Updated the 4.1.10 translation cache's justifying comment accordingly — it no longer claims a strict "pure function" determinism guarantee (that relied on temperature=0.0), reframed as trading a little per-call sampling diversity for consistency + speed on repeat queries, which still holds at a non-zero configured temperature.
- ✅ 4.1.16 **Deleted `backend/nl_search/router.py`, an unreferenced dead-code duplicate of the live `backend/api/nl_search/router.py`.** (`commit c67126e`) Confirmed via grep: `main.py` only ever mounted the `api/nl_search` copy, and `backend/nl_search/__init__.py`'s public surface never referenced the other one. Not just inert — it nearly got edited in place of the real router during 4.1.15 (fixed "for consistency" before this cleanup caught it), exactly the failure mode an unreferenced duplicate invites.

**Tests (4.1.9-4.1.16):** 8 new for the bare-direction rule + translation cache (`test_parser.py`, `test_ai_parser.py`); 4 new for the confidence rescale (`test_trend_engine.py`); 2 new for the 429 fix (`test_ai_manager.py`, one per provider class). Ran only the scoped test files touched by each fix (127 / 358 / 75 passed respectively, per fix) rather than the full suite each time, per standing instruction — full suite not run for this addendum as a whole.

## Phase 4.2 — AI-Powered Features — ✅ DONE (2026-09-09)

**Trigger:** User request — "what can we do with AI for more functionality," the exact "separate decision" Phase 4.1's own open questions deferred. Planned via a research + design workflow (3 parallel Explore agents mapping the alerts engine/scheduling primitives/frontend architecture/digest data sources, 1 Plan agent synthesizing a sequenced approach, spot-checked against the real code, approved via plan mode) rather than designed ad hoc. Built one feature at a time with a live check-in after each, per explicit rollout instruction — not a single continuous push.

**Items:**
- ✅ 4.2.1 **News/fundamentals/divergence-aware AI Analysis, plus a real dead-code bug fixed in the same PR.** (`commit 12b6623`) Enriched `build_context()` — the one function every other AI feature also calls — with three new sections: `backend.aux_data`'s News and Fundamentals providers (built in an earlier phase, never wired to the AI) and `backend.divergence`'s DivergenceEngine (same story). Each independently gated (`include_news`/`include_fundamentals`/`include_divergence`, default `True`) so a batch caller (the digest, below) can skip the extra I/O per symbol. **Real bug found during the research pass:** `build_context()` step 8 and NL search's `JustTransitionedFilter` both imported a `trend_transition_engine` singleton and called `.get_history(symbol=...)` — neither exists; the broad `except` silently swallowed the error every time, so `trend_transition` had been an empty dict in every AI analysis ever produced, and that NL search filter had always returned `False`. Fixed both to pull the already-warmed `TrendEngine`'s own score history and run `TrendTransitionEngine.latest()` on it directly. Verified live: a real AAPL analyze call naturally cited `bullish_reversal` and `bearish_volume_divergence` in its supporting/risk factors — confirmed via a direct `build_context()` call these were genuine detected signals, not coincidental phrasing.
- ✅ 4.2.2 **Enabled the news/fundamentals flags — which surfaced a real external-library bug.** `AUX_NEWS_ENABLED`/`AUX_FUNDAMENTALS_ENABLED` were `false` in the live `.env`, so 4.2.1's new sections were correctly wired but silently empty. Turning them on (`commit 41d93dc`) revealed `yfinance==0.2.36` raising a raw `JSONDecodeError` against Yahoo's current API for both `.news` and `.info` — a well-known yfinance version-lag issue. Upgraded to `yfinance==0.2.66` (deliberately the latest same-major patch, not the 1.7.0 major bump available — smaller blast radius). Confirmed the market-data quote/bar path doesn't use the `yfinance` library at all (it hits Yahoo's chart API directly via `curl_cffi`, specifically to avoid this exact class of instability per its own docstring), so the bump's blast radius was isolated to the three `aux_data` providers. News needed a code fix on top of the version bump too: yfinance restructured `ticker.news` into a nested `{"id", "content": {...}}` envelope; fixed the provider's parsing with a fallback to the old flat shape. Also found and fixed 5 CSS rules (from this session's own earlier work) referencing an undefined `--accent` variable (only `--accent-primary` exists) while styling later items. Verified live: `/api/aux-data/news/AAPL` went from 0 items (across every watchlist symbol) to 10 real headlines; a real analyze call cited "Analyst buy recommendation with target $323.86" and "EPS growth of 28.7%" directly from fundamentals.
- ✅ 4.2.3 **Daily/session AI digest.** (`commit 3b16dd0`) A watchlist-wide digest (premarket/close) combining market regime, top bullish/bearish movers (each with a feature-1-enriched AI blurb), RSI extremes, and MTF-alignment counts, AI-narrated. No scheduler exists anywhere in this codebase (confirmed absent: APScheduler/celery/croniter/rq-scheduler) — reused the ingestion service's existing hand-rolled loop style rather than adding a dependency for one twice-daily job, with one improvement: "fire once we notice the target time has passed today" instead of a narrow time-window gate (robust to any tick cadence, no minute-alignment risk). **Real bug caught by its own test before shipping:** the original mover-selection logic took "top N regardless of sign" for bullish first, then filtered bearish to exclude claimed symbols — on a small watchlist this let bullish silently consume every symbol, leaving bearish always empty. Fixed by splitting into genuinely-positive/negative candidate pools before taking top-N. Verified live: a real digest generation produced 5 real movers with real signed scores and a correct all-bullish/no-bearish split matching actual market conditions that day.
- ✅ 4.2.4 **Alert-triggered AI commentary.** (`commit 074205a`) A short AI note explaining why an alert fired, generated out-of-band (a new RQ job on the existing `marketlens-workers` queue, not a dedicated one) and written back into the `AlertTrigger` row itself rather than a separate job-status table — the trigger row already exists and is meaningful with or without the commentary. Both trigger-persist paths (an async request handler and a live-tick callback that gates every other alert evaluation for that tick) are latency-sensitive, so generation never runs inline. Also built the per-trigger list `AlertsCard.tsx` had been missing all along — it fetched the full trigger array already but only ever rendered an aggregate count. Verified live end-to-end through the real async path (not just a direct function call): a signal_equals alert fired, the trigger committed immediately with `ai_commentary=null`, and the RQ worker independently wrote real AI-generated commentary within seconds.
- ✅ 4.2.5 **Two pre-existing alert-firing bugs found while verifying 4.2.4 live, fixed as an explicit follow-up.** (`commit 4040238`) Both confirmed pre-existing via git log (predate this whole session) and unrelated to AI commentary specifically:
  1. `engine_seeder.py`'s `dispatch_quote()` never passed `symbol` to registered callbacks, but `AlertsEngine._on_quote()` requires one — every live quote tick threw "missing 1 required positional argument," silently caught and logged, meaning price-based alerts (`price_above`/`price_below`/`pct_change_above`) had never actually fired from a live tick. Its sibling `dispatch_bar()` had always correctly passed `symbol=symbol`; `dispatch_quote()` was the inconsistent one. Fixed to match.
  2. `register_for_alert()`/`unregister_for_alert()` only branch on price/bar condition types — `signal_equals` (the one condition type in neither bucket, confirmed against the full 15-entry `VALID_CONDITION_TYPES`) fell through both entirely and never touched `_alerts_cache`, so a freshly-created `signal_equals` alert didn't evaluate until the next full server restart, despite the method's own docstring promising immediate evaluation. Fixed by adding a dedicated branch.
  Verified live, both together: a `price_above` alert fired within 2 seconds of creation off a real live quote (previously: never); a `signal_equals` alert fired within 8 seconds with zero restart (previously: only after a restart).
- ✅ 4.2.6 **Conversational AI chat panel.** (`commit dc70ad0`) A free-form back-and-forth chat about one symbol, grounded in the same `build_context()` every other feature uses. Net new UI and backend surface — no chat/message-list component, conversation-storage model, or tool-calling pattern existed anywhere in this codebase before. Scoped deliberately tight: single-turn-per-message (context rebuilt fresh every message, not cached as server-side "memory"), symbol-scoped not user-scoped (no auth system in this app), read-only relationship to features 1-3 (can read an alert trigger's own facts when opened from one, never triggers new analysis/digest/commentary itself), no streaming. Verified live in both modes: a plain symbol chat gave a grounded reply citing real trend/confidence numbers, with a follow-up correctly getting a freshly-recomputed (differently grounded) answer; a chat opened scoped to a real, just-fired alert trigger correctly referenced that trigger's own facts in its reply.

**Tests:** 40 new for 4.2.1 (context enrichment, transitions regression, news/fundamentals, divergence, extracted series module); 1 new regression for 4.2.2 (yfinance's new nested news shape); 18 new for 4.2.3 (digest payload/narration/scheduler/router); 12 new for 4.2.4 (commentary generation, engine integration, router serialization); 4 new for 4.2.5 (dispatch_quote symbol passing, signal_equals cache registration); 26 new for 4.2.6 (chat logic, repository CRUD, router). ### Addendum (2026-09-10) — Items 4.2.7-4.2.10: clearing the deferred open questions

Per explicit user request, all three open questions Phase 4.2 left behind (plus one gap noted only in-session, not in this doc) were cleared in one follow-up pass:

**Known, surfaced to the user, deliberately not changed — the ranking
semantics.** Every one of these is a *meaning* decision about what the
rankings are supposed to say, not a wiring bug, so they were reported
rather than edited:

1. `_build_strongest_bearish` mirrors `_build_strongest_bullish` — it sorts *ascending on the same directional metric*, so the two categories return the same symbols in reverse order rather than genuinely bearish ones. Live: bullish `['QQQ','SPY','IWM','VIXY']`, bearish exactly reversed.
2. `_build_biggest_improvement` / `_build_biggest_deterioration` rank on `trend_strength`, which carries no direction — strongest-bearish ranks as "biggest improvement" if its magnitude is largest.
3. `rank()` sets `total_eligible = len(candidates)` identically for all seven categories, so it reports the pool size, not each category's own eligibility.
4. `calculate_signed_total_score`'s denominator is the sum of absolute weights, letting unsigned magnitude factors dominate the signed ones, and `Scanner.score_weights` is never passed in. Every live score observed is positive (18.7-38.1), which makes the app's own `<= -30` bearish band unreachable.
5. `TopMoversCard.isBullish()`'s client-side re-filter now drops every row: all scores are positive and `HIGH_VOLUME` appears in neither the bullish nor the bearish signal Set, so it degenerates to `total_score > 0`. Net effect today — the bullish card lists the watchlist's symbols and the bearish card renders empty. This one is downstream of (1) and (4): removing the client filter without also sign-filtering the backend pool would just put the same reversed list in both cards.
