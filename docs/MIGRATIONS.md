# Database Migrations

MarketLens uses [Alembic](https://alembic.sqlalchemy.org/) to manage the SQLite schema. All 12 ORM tables are tracked in versioned migration scripts.

## Quick start

```bash
# Apply all migrations (creates the schema if the DB doesn't exist yet)
alembic upgrade head

# Check for drift between the ORM models and the live DB
alembic check

# Show the current migration version
alembic current
```

## Workflow

### Adding a schema change

When you add or modify an ORM model:

```bash
# Generate a new revision (auto-detects changes via --autogenerate)
alembic revision --autogenerate -m "add position_size to backtest_runs"

# Review the generated file in alembic/versions/
# Correct any subtle differences alembic couldn't infer (defaults, indexes, etc.)

# Apply it
alembic upgrade head
```

### Rolling back

```bash
# Roll back one migration
alembic downgrade -1

# Roll back to a specific revision
alembic downgrade <revision>
```

### Offline mode (no DB connection)

Generate the SQL without connecting:

```bash
alembic upgrade head --sql
```

## Baseline migration

The initial migration (`20260828_8175af1a213e_initial_schema.py`) was generated by running alembic against a blank DB, capturing all 12 tables at the Phase 20 schema state. It covers:

- `alerts`, `alert_triggers`
- `backtest_runs`, `backtest_trades`
- `bars`, `quotes`, `market_status`, `provider_status`
- `experiments`, `historical_signals`
- `watchlists`, `watchlist_symbols`

## `create_all()` vs. Alembic

`Base.metadata.create_all()` (called at startup in `init_db.py` and `run.py`) is still the **canonical way to bootstrap a fresh DB**. Running `alembic upgrade head` on a brand-new DB produces an identical schema. Both paths are equivalent — Alembic is the migration layer on top of the same schema.

The existing DB was stamped to the baseline migration after Alembic was set up, so it is already at head. New schema changes should go through Alembic exclusively from now on.
